Do not place seed phrases, private keys, or wallet export files in this repository or the smoke notes. Keep transaction identifiers and public addresses as the evidence.

UniSat [lists Bitcoin Testnet and Bitcoin Testnet4 as separate chains](https://docs.unisat.io/developer-support/open-api-documentation/unisat-wallet/supported-chains), both with the `tBTC` unit. Its [mobile transfer instructions](https://docs.unisat.io/products/unisat-wallet/how-to-deposit-withdraw-assets) describe signing and sending with no raw-hex export step. Its separate [mobile developer interface](https://docs.unisat.io/developer-support/open-api-documentation/unisat-wallet/connect-with-unisat-mobile-wallet) documents a `signPsbt` deeplink and a response deeplink, while the [wallet API](https://docs.unisat.io/developer-support/open-api-documentation/unisat-wallet) specifies that `signPsbt` returns signed **PSBT hex**, not raw transaction hex. A compatible helper is an implementation path, not a completed or device-tested workflow. Keep this wallet on Bitcoin Testnet; do not transfer the recovery phrase into another tool to satisfy the gate.

The A2 path is a separate [Sparrow desktop wallet](https://sparrowwallet.com/download/) with `testnet4` selected. [Sparrow's configuration](https://github.com/sparrowwallet/sparrow#configuration) distinguishes `testnet4` from legacy `testnet` (Testnet3); its [feature guide](https://sparrowwallet.com/features/) says a final signed transaction can be saved or copied from the hex view. [Bitcoin Core](https://github.com/bitcoin/bitcoin/blob/master/src/chainparamsbase.cpp) marks Testnet3 deprecated and recommends Testnet4. Generate and back up the wallet in Sparrow, never in ChainPay or this repository. The separately funded wallet leaves the existing UniSat UTXO and recovery phrase untouched.

The Sparrow address was first checked against Testnet3 at 2026-10-26 02:06 UTC and correctly showed zero there; the wallet was actually on Testnet4. At 2026-10-26 14:28 local time, a packaged ChainPay 44.4.5 watch on Testnet4 displayed the unconfirmed 50,000-sat faucet payment, one UTXO, and the matching transaction. See the [live evidence](phase-5-slice-a-bitcoin-watch-live-2026-10-26.md). Early packaged smokes used a temporary localhost relay because direct Node `fetch` timed out. A direct [Electron `net.fetch` probe](https://www.electronjs.org/docs/latest/api/net) returned HTTP 200 from the public Testnet4 API; the Bitcoin main-process host now uses that Chromium networking path. The rebuilt package synced tip 158197, refreshed the posted transaction to 23 confirmations, and reviewed the unbroadcast low-fee candidate directly against the public provider. No relay was configured for that smoke.

The manual broadcast review now queries the configured provider's optional Mempool `v1/fees/recommended` endpoint. If the signed fee is below `minimumFee`, the immutable review includes a warning; a changed estimate requires a new approval before broadcast. A 404 or unavailable fee-advice endpoint leaves the review usable, so the warning is not a guarantee of relay acceptance. [Bitcoin Core 30.0 changed its default relay minimum to 0.1 sat/vB](https://github.com/bitcoin/bitcoin/blob/master/doc/release-notes/release-notes-30.0.md), while nodes may configure different policies and [Mempool exposes current recommended fees](https://mempool.space/docs/api/rest). A hardcoded 1 sat/vB rule would misstate the current Core default. The full desktop suite passed after this change (1,223 tests, 4 skipped), along with typecheck, lint, and production build.

A rebuilt Linux package reviewed the earlier signed candidate `60926ca8…0a755` through the same GET-only Testnet4 relay. It identified the 54-sat fee at 0.49 sat/vB and displayed the warning against the provider's then-current 1 sat/vB suggestion. The candidate's transaction endpoint still returned 404 afterward, and the original posted accounting record remained intact. No broadcast was attempted.
